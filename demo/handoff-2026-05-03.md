## Three things to know before you touch anything

1. **The verify pipeline is the gate.** If you push and `Verify` workflow goes red, branch protection will refuse merge of any PR. `npm run verify` matches CI exactly. The new `eslint.config.mjs` is a flat config — `next lint` no longer works (it injects legacy flags); use `npm run lint` which calls `eslint .` directly.

2. **Audits gate the build now.** `.github/workflows/security-audit.yml` queries the GitHub API on every push and fails CI if any open Dependabot or CodeQL alert is at high/critical. If you introduce a new vulnerable dep or pattern, you'll see the failure immediately. To add a known-safe exception inline:
   - `// audit-safe: A3 reason="<specific reason>"` (app-security)
   - `// audit-safe: A4 reason="<specific reason>"` (cross-tenant SQL)
   - `# audit-safe: G1 reason="<specific reason>"` (CI/CD audit, in YAML files)

3. **Heatmap data flow is symmetric — keep it that way.** The ingest (`/api/analytics/events`) and the query (`/api/admin/heatmaps`) BOTH call `resolveTenant(host)` and BOTH fall back to `process.env.DEALER_ID ?? "00000000-0000-4000-a000-000000000001"`. If you change one, change both — mismatch = invisible events (we lived this for half a session).

- ⚠️ **Nick flagged this for review — DO NOT just set these blindly:**
  `MFA_BACKUP_CODE_PEPPER`, `AGENCY_API_KEY_PEPPER` — added by HMAC fixes
  in commit `132c533` to close two CodeQL "insufficient password hash"
  findings (`mfa.ts` `hashBackupCode`, `bulk-provision/route.ts` agency
  API key lookup).

  **Why peppers exist:** they're a server-side secret that gets mixed
  into the hash so a stolen DB alone can't be brute-forced offline.
  In principle good. In practice, the way it landed has problems:

  1. **Backwards-compat is broken.** Existing rows were stored as raw
     `sha256(code)`. Once the env var is set, lookups compute
     `HMAC(pepper, code)` and won't match the old rows. Every existing
     MFA backup code becomes invalid; every existing agency API key
     stops authenticating. There's no migration that re-derives them.

  2. **Set-and-forget hazard.** If the env var is ever lost, rotated,
     or differs between environments, every backup code + API key
     becomes silently invalid. There's no graceful fallback.

  3. **Pepper-vs-bcrypt tradeoff wasn't discussed.** For passwords,
     bcrypt/argon2 with proper cost factors is the standard answer.
     HMAC+pepper is a weaker primitive that depends entirely on the
     pepper staying secret. The fix may have been the wrong shape.

  **Action items for next session, IN ORDER:**
  - Query: `SELECT COUNT(*) FROM users WHERE mfa_backup_codes IS NOT NULL`
    and `SELECT COUNT(*) FROM agency_api_keys WHERE active = TRUE` —
    confirm whether existing rows would be invalidated.
  - If counts are 0: setting the peppers is safe.
  - If counts are non-zero: ship a dual-verify path FIRST (try HMAC,
    fall back to legacy sha256, rewrite to HMAC on success) so existing
    users aren't locked out, THEN set the env var.
  - Consider whether HMAC+pepper is even the right answer for backup
    codes — bcrypt/argon2 might be a better fit. The CodeQL rule
    accepts any keyed/iterated hash; we picked HMAC for synchronous
    speed but it's worth a second look.
  - Until resolved: **do not deploy with these env vars set.** The
    code path falls back to legacy sha256 when the env var is unset
    (verify this in `mfa.ts` + `bulk-provision/route.ts`); CodeQL will
    flag the finding as still-open but production won't break.
