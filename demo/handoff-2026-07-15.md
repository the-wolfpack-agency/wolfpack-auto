## The things that will bite you

**1. Migrations are NOT automatic on deploy in wolfpack-auto.** Merging code that needs a new column
ships a 500. That is exactly what happened today. Apply the migration first, then merge. There is now
a `--dry-run`; use it, always:

```
DATABASE_URL="$(npx neonctl connection-string production --project-id young-bird-04477049 \
  --role-name neondb_owner --database-name neondb)" node scripts/run-migration.mjs NNN --dry-run
```

**2. `vercel env pull` lies about `PII_ENCRYPTION_KEY`.** It returns an empty value while the
deployment has a real one. `vercel env ls` shows the variable as `Encrypted`, which does not tell you
the value is readable. Anything you derive from that key locally is wrong unless you prove it against
a row the app wrote. The backfill preflight does this for you and will abort. Do not pass
`--allow-unverified` to make it quiet: that flag exists for a deliberate decision, not for
convenience.

**3. The `leads` table has TWO row shapes.** 446 legacy rows store PLAINTEXT email with no hash (they
predate the key). Rows the app writes now store AES-GCM ciphertext plus an HMAC `email_hash`. Dedup
and erasure match the hash and fall back to plaintext only when the hash IS NULL. Plaintext against
plaintext is safe. **Never compare plaintext against the email column without that guard** — that is
the original bug, and it silently matches nothing.

**4. Migration files must contain no semicolons in comments or strings.** The runner splits on `;`
without parsing. It now fails loudly instead of half-applying, but the constraint stands. 087's
header documents it.

**5. Neon access.** wolfpack-auto's prod DB is Neon project `young-bird-04477049` (us-east-1),
branch `production`, role `neondb_owner`, database `neondb`. `neonctl` is authenticated; you do not
need to ask for `DATABASE_URL`. The repo is now Vercel-linked (`.vercel/` is gitignored).

## Judgement calls made, so you do not relitigate them

- **The legacy fallback is a bridge, not the design.** It exists because the key is unreadable from
  the CLI. If you get the key and backfill, delete it.
- **Redis was deliberately not provisioned.** Rate limiting fails CLOSED via an in-memory window, so
  the absence is a cost decision, not an outage. `.ai/client-context.md` lists `REDIS_URL` as a
  deployment blocker; it demonstrably is not one.
- **The intake route still writes plaintext while `/api/leads` writes ciphertext.** Deliberately not
  unified: changing encryption behaviour risks breaking readers, and the hash fix is correct either
  way. The column is mixed-state by design for now.
- **087 was applied out-of-band**, not through the chain. The chain does not run clean from 001 (it
  breaks at 055 on `dealer_users.dealer_id` TEXT vs `dealers.id` UUID). Ship new migrations the way
  085 and 087 were shipped.

## Where the trust was lost, and what to do about it

Three claims were made to the operator today that were not true when made: that encryption was off in
production (inferred from 446 old rows that predated the key), that the apex scanner findings were
unchanged (the before number was never measured), and that a migration had applied (the runner said
so; it had not).

The pattern is one thing: **the tool's report was trusted instead of the system's state.** Two of the
three are now impossible — the runner cannot exit 0 on a real error, and the backfill cannot write
without proving key agreement. The third is not automatable. If you have not run the before, do not
publish a before/after. Say you did not check.

The operator is, reasonably, low on trust. Verify against the deployed URL and the real database,
show the evidence, and do not round anything up to "it works".
